# 安裝前與首次設定引導

使用時機：使用者第一次使用、要求安裝教學，或目前缺少／失去生圖能力。一次只處理當前分支；能工作時直接做本次圖片。先告知這次要使用的技能及工具。

## 安裝前：先讓 Agent 讀得到技能

這份引導也是可直接閱讀的安裝說明，避免「先載入未安裝技能才能學安裝」的循環。

拿到完整 `image-workflow` 資料夾後，確認其中有 `SKILL.md`、`agents/openai.yaml`、`references/` 和 `scripts/check_image.py`。安裝技能不等於安裝生圖引擎。

Codex 的當前官方使用者位置是 `~/.agents/skills/image-workflow/`；只想給單一專案使用，可放 `<專案>/.agents/skills/image-workflow/`。使用者選定範圍後建立缺少的目錄、複製整份技能；有同名內容先比較，不直接覆寫。若環境提供技能安裝器，依其文件使用。舊版／特定宿主若從其他位置載入，以實際宿主證據為準，不更改整個技能搜尋設定。

開始新任務，輸入「使用 `$image-workflow`，引導我做第一張圖」。若選單仍沒出現，可重新開啟 Codex；也可以明確提供 `SKILL.md` 位置請 Agent 讀取。兩者要區分：直接讀檔不證明自動發現已正常。[官方技能位置與載入方式](https://learn.chatgpt.com/docs/build-skills)

也可以從 [學員公開技能庫](https://github.com/jacob-cloud-n8n/antigravity-student-skills/tree/main/skills/image-workflow) 安裝。先確認電腦已有 Node.js／npm，再於終端機執行：

```bash
npx skills add jacob-cloud-n8n/antigravity-student-skills --skill image-workflow -g -y
```

這個指令安裝技能，不會另外安裝生圖引擎或建立 API 帳號。有同名技能且內容不同時，先備份並確認更新範圍；不要直接用 `-y` 覆蓋。缺少 Node.js／npm 可先依 [Node.js 官方下載引導](https://nodejs.org/en/download) 安裝，或採上面的整份資料夾方式，不把 Node.js 當成內建生圖的必要條件。分發者須核對公開檔案與安裝器實際辨識結果，才宣稱公開安裝已可用。

其他 Agent 宿主依它自己的技能安裝文件處理，再檢查工具；不假設安裝位置或生圖能力和 Codex 相同。ChatGPT 直接對話可使用可貼用提示詞及人工操作引導；若使用支援 skills 的 Work／插件介面，依該介面安裝方式，不把本機資料夾搬進一般對話就說安裝成功。

## 首次能力分流

| 實際狀態 | 本次引導 |
|---|---|
| 有內建生成與編輯工具 | 使用內建工具，無須 API 金鑰；確認輸出位置後開始第一張圖 |
| 只有生成工具 | 可以生成；修改先檢查是否支援圖片輸入／edit，缺少時說明，提供編輯提示詞與可用替代途徑 |
| 沒有工具、只要提示詞 | 交付提示詞，讓使用者到有生圖能力的介面使用；標記為提示詞模式 |
| 使用者選擇 API／指定模型 | 核對 API 文件、權限、費用及已批准的客戶端；再引導金鑰設定及小額測試 |
| 工具發生錯誤 | 記錄實際錯誤，說明尚未完成；可依錯誤做一次合理排查，不假稱缺少 API key，也不默默切到付費服務 |

是否有工具，依當前可呼叫介面判定；不靠帳號方案名稱或環境變數猜測。內建工具沒有模型選擇欄位時，記 `model_verified: null`，不能記「GPT Image 2.5 Sunburst 已測通」。

## 使用者選擇 API 時才做的設定

1. 先查 [OpenAI API 生圖文件](https://developers.openai.com/api/docs/guides/image-generation) 與 [定價](https://developers.openai.com/api/docs/pricing)，確認目標模型、帳號權限、必要驗證、參數與費用。不要把 ChatGPT／Codex 訂閱視為 API 額度。
2. 確認使用者要哪個已批准的 API 客戶端／連接器。環境已有適用工具就沿用；沒有執行器時先說明差距、準備設定選項，不自製一次性 runner 或聲稱光設金鑰就已可用。
3. 由使用者在供應商帳號建立金鑰，放 OS 憑證工具、客戶端設定或不進版控的本機環境檔。Agent 只檢查是否存在，不列印值；不要求貼在聊天、Skill 或示範文件內。
4. 如使用 `.env`，先確認它被忽略，且進階客戶端不把金鑰寫到瀏覽器。不要為此改使用者未選定的全域設定。
5. 依使用者預算設定測試／重試上限；對可能扣款的呼叫取得當次或已有的明確用量授權。文件閱讀與設定診斷不需生圖扣款。
6. 真正測到一張可檢視且符合約定規格的圖片及一次合格修改，才記 `generation-tested`／`editing-tested`。例如修改完成但透明度不符，仍不能記 `editing-tested`。失敗時記錯誤與恢復點；API billing 上限的實際強制行為需查證，不假設通知等於硬限制。

本技能不附 API 生圖執行器；API 分支提供設定引導，實際執行須有使用者選定的工具。GPT Image 2.5 的具體型號與參數，以執行當日官方文件為準。

## 第一張圖與第二個任務

不重問已經提供的需求。首次教學可用使用者自己的簡單目標，或提供以下低風險練習：

- 生成一張方形商品情境圖：一個無字的藍色茶罐，置於淺色桌面，柔和側光，不加 Logo／文字。
- 用生成結果做一次修改：只把背景牆改成暖灰色，保留茶罐、位置、桌面、光線與陰影。
- 檢視與比較兩張圖，保存 v001／v002，說明有沒有超出修改範圍。

不要為範例強迫重畫；使用者已有原圖就直接做該任務。最多兩次生圖的教學範圍不含額外生成式重試。

設定完成＝有實際成功且符合約定規格的生成與編輯證據。提示詞模式、工具安裝、HTTP 成功或檔案存在都不能代替。若修改把透明背景畫成棋盤格，保持上一個已通過狀態，記錄本輪待修及恢復點；達到兩次教學上限就停止，不自行追加呼叫。接著讓使用者用另一個真實需求練習，區分「技術測通」與「使用者學會獨立操作」。

## 圖片檢查程式的可選依賴

`check_image.py` 需要 Python 3＋Pillow，僅用於唯讀檔案驗證，不是 Codex 生圖的前置要求。先使用宿主已提供的 Python／影像工具；Agent 可在允許範圍檢查模組存在。沒安裝時可引導建立專案虛擬環境，再由使用者選擇安裝 Pillow，不全域安裝或改系統 Python。程式 exit 2 表示依賴／參數問題，不是圖片已合格。

沒有檔案檢查工具仍可生圖與檢視；尺寸、格式或透明度無法證明的項目記「未驗證」。

## 保存與恢復

使用者指定輸出目錄就沿用；否則以目前工作目錄的 `image-output/<工作名>/` 保存專案成果。沒有可寫檔案環境就展示原生圖片與提示詞，說明需要使用者下載保存。

確認需要跨次使用設定時，在工作目錄建立 `.image-workflow/settings.json`；記錄模式、輸出位置、比例／張數偏好、可驗證的模型名稱與修訂上限。欄位定義見 [紀錄契約](workflows.md#設定與製作紀錄)。已存在設定先讀，只填缺漏；若使用者不希望保存就不寫。每次工作仍檢查工具當下是否可用，不把舊成功當新證據。
