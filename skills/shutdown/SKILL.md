# 收工同步助手（三層級）

對話結束前，把這次的工作保存到專案建到的每一層：

| 層級 | 收工動作 | 給誰看 |
|------|---------|--------|
| L1 本地 | 更新 `AGENTS.md` 進度＋改寫 `handoff.md` | 下一個 session 的任何 Agent、任何電腦 |
| L2 GitHub | 敏感掃描 → 挑檔案 → commit + push | 版本歷史＋雲端備份 |
| L3 筆記 | 詳細紀錄（決策原因、踩坑細節） | 未來需要完整脈絡的自己 |

## 核心原則

1. **開工是「讀」、收工是「寫」**——handoff.md 是收工的必寫項，這是跨電腦／跨 Agent 交接的生命線
2. **不在真空裡執行**——先從對話脈絡盤點今天做了什麼
3. **只動需要動的**——沒實質進度（只是問問題、沒改檔案）就不跑同步
4. **人類在環**——commit 訊息先給草稿等點頭；不確定要不要 add 的檔案先問；diff 給人看
5. **精簡與詳細分家**——handoff.md 只放交接必需資訊（一頁內讀完），決策原因與踩坑細節寫 L3 筆記，兩邊不重複

> 🗣️ 收工口訣：搜敏感 → 寫交接 → 看 diff → 挑檔案 → 點頭才提交推送 → 回填回報

## 層級偵測（收工看「這個專案」建到哪層）

- **L1**：專案有 `AGENTS.md`／`handoff.md` → 更新（沒有就提議先跑「初始化專案」）
- **L2**：專案有 `.git` → commit + push
- **L3**：`AGENTS.md` 登記了筆記位置 → 寫詳細紀錄（Obsidian 或 `docs/工作筆記.md`）

> 低層級電腦打開高層級專案：做得到的照做，做不到的在 handoff.md 註明（例：「本次在無 Obsidian 的電腦收工，L3 筆記未更新」），回到高層級電腦時補。

## 收工 SOP（依序執行）

### 0. 判斷有無實質進度

只是問問題、討論、沒改任何檔案 → 不跑同步，簡短收尾即可。

### L1：更新藍圖與交接檔（永遠執行）

1. **盤點本次成果**：從對話歷史摘要——完成了哪些檔案、做了什麼決定、踩了什麼坑。
2. **更新 `AGENTS.md`**：
   - 路線圖 checklist：勾掉完成項、新增發現的待辦
   - 「資料夾結構」有新增重要檔案就補
   - 若已啟用學員第二大腦，保留其狀態與相對路徑；日常收工不擅自改架構
3. **改寫 `handoff.md`**（**整份重寫**，不是往下堆）：
   - ⏯️ 目前做到哪：本次最後完成的動作
   - 🚦 目前狀態：可運行？哪些做一半？
   - ➡️ 下一步：具體、可執行的 1-3 項
   - ⚠️ 注意事項：新踩的坑、暫時 workaround
   - 🕐 最後更新：時間＋更新者（Agent 名 @ 電腦名）＋ Git push 狀態（先寫「待推」，L2 完成後回填）＋ L3 筆記狀態

> **做到一半要中斷**：一樣要寫 handoff——「目前做到哪」寫中斷點、「下一步」寫接續的第一個動作。沒寫交接檔的中斷＝下次從零開始。

### 選配：學員第二大腦寫回（有明確啟用標記才做）

若 `AGENTS.md` 明列「第二大腦／狀態：啟用」及有效相對路徑：

1. 盤點本次新增的原始資料、可重用知識與可交付成果，排除純聊天與一次性草稿。
2. 先顯示一份寫入預覽：每項列出目標相對路徑、類型、1–3 句摘要與來源。**取得使用者確認後才寫入二腦**；「收工」本身不等於同意所有分類結果。
3. 原始資料寫入 `Clippings/<專案>/`；知識寫入 `知識庫/<專案>/`；成品寫入 `創作庫/<專案>/`。沿用既有檔案與分類，不覆蓋不明內容。
4. 個資／內部資料先盡一次性告知義務並提供代號化選項。使用者確認有權且接受風險後可繼續，不反覆勸阻；API key、token、密碼、Cookie、私鑰、驗證碼與助記詞一律排除。
   - 「可在本機二腦使用原始資料」不等於「可提交 Git」；仍須依下方敏感資料掃描排除或先代號化。
5. 只有知識頁真的新增或更新時才維護 `知識庫/index.md`。
6. 在 `工作日誌/log.md` 底部追加本次日期、完成事項、變更頁與下一步；不得改寫舊紀錄。
7. 已啟用第二大腦時，`工作日誌/log.md` 可作為 L3 詳細紀錄；不要再把同一內容重複寫入 `docs/工作筆記.md`。

缺少啟用標記或路徑不存在時，跳過本節並維持原收工流程；不猜測、不自動建立。

### L2：git 同步（專案有 `.git` 才做）

4. **敏感資料掃描**（提交前的硬性 gate）——在將要提交的內容中檢查：
   - 關鍵字：`api_key`、`apikey`、`token`、`secret`、`password`、`private_key`、`client_secret`
   - `.env` 檔案出現在 `git status`（不該出現！）
   - 程式碼中硬編碼的憑證
   - 真實個資（客戶／學生的姓名、電話、地址）

   命中 → 先移出提交範圍、或補進 `.gitignore`，處理完再繼續。
5. `git status --short`＋`git diff` 看變動 → **只 stage 本次相關檔案**（不用 `git add .`；進階可用 `git add -p` 逐段挑選）→ untracked 的不明新檔先問使用者。
6. 擬**繁體中文** commit 訊息：標題用前綴＋動詞（`feat:`／`fix:`／`docs:`／`chore:`／`refactor:`／`test:`），正文 3-5 條 bullet 描述變動＋為什麼 → **給使用者過目，點頭才 commit**。
7. commit → `git push`。
8. **回填 handoff.md 的 Git push 欄**：成功 → `✅ 已推`；失敗 → `❌ 未推（原因）`，並在回報中標紅提醒（沒推成功，另一台電腦就拿不到 GitHub 備份）。

### L3：詳細紀錄（有登記才做）

9. 更新筆記（Obsidian `專案工作流程.md` 或 `docs/工作筆記.md`）：
   - 「⏯️ 上次做到哪」段：同步 handoff 摘要
   - 「🗓️ 最近更動紀錄」表格：加一行（日期＋摘要＋同步狀態）
   - 「🕳️ 踩坑筆記」：有新坑就補（含原因與解法，這裡寫詳細版）
   - 決策紀錄：本次做了什麼取捨、為什麼（handoff 不放這些，放這裡）
10. 更動紀錄表格超過 30 行 → 提醒使用者歸檔到 `歷史日誌.md`。

### 回報（層級 checklist）

```
✅ L1 本地：AGENTS.md 進度已更新、handoff.md 已改寫（更新者：<Agent> @ <電腦名>）
✅ L2 GitHub：<repo> 已 commit + push（<commit 標題>）
✅ L3 筆記：<路徑> 已補紀錄
⚠️ 手動處理：<例：本次新增了本機 API key 設定，另一台電腦要手動建>
```

沒做到的項目用 ⚠️ 或 ❌ 並說明原因。

## 不該做的事

- ❌ 對「沒實質進度」的對話也跑同步
- ❌ 沒更新 handoff.md 就收工（那是下次開工的唯一線索）
- ❌ commit message 寫「更新」「修改」這種沒資訊的字
- ❌ 用 `git add .`、或自動 add untracked 的不明新檔／敏感檔
- ❌ 沒給使用者看 commit 訊息草稿就直接提交
- ❌ 把該寫進 L3 的長篇細節塞進 handoff.md（交接檔要保持一頁內讀完）
- ❌ 未預覽並取得確認就把聊天內容批次寫進學員第二大腦
- ❌ 同一份詳細紀錄同時寫入二腦 log 與 `docs/工作筆記.md`
- ❌ 為學員預設建立每日自動整理排程

## 與開工（startup）的對偶關係

| 面向 | 收工 | 開工 |
|------|------|------|
| AGENTS.md / handoff.md | **寫入** | **讀出** |
| Git 動作 | 掃描 → 挑檔 → commit + push | status + fetch（不 pull） |
| L3 筆記 | 寫詳細紀錄 | 只列路徑、需要才讀 |
| 對外副作用 | 推 GitHub、改檔案 | 無 |

## 注意事項

- 所有訊息使用**繁體中文**。
- Google 雲端硬碟內的 repo 在 Windows 首次操作若遇 git 寫入錯誤：`git config windows.appendAtomically false`（Mac 不需要）。
