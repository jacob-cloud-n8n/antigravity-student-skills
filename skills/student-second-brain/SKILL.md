# 學員版第二大腦

把第二大腦做成一個可持續使用的本機 Markdown 專案。採用 Karpathy LLM Wiki 的核心精神，但以初學者、單一或少量 Agent、低維護成本為前提。

## 成功標準

完成後應同時做到：

1. 學員只有一個共用第二大腦，內容可依專案分類，不散落在多個 repo。
2. 原始資料、整理後知識、創作成果與工作歷史分開保存。
3. 每次寫入前先讓學員看見目標位置與摘要，確認後才寫檔。
4. 新對話能透過索引、近期日誌和交接檔接續，不必重述全部背景。
5. 整理後內容能追溯到來源，未知、推測與衝突不被寫成確定事實。

## 預設架構

初始化時以目前資料夾作為第二大腦根目錄；不要再建立第二個 Git repo。若已有相同用途的資料夾，先盤點並沿用，只補缺口、不得覆蓋。

```text
第二大腦/
├── AGENTS.md
├── handoff.md
├── Clippings/       # 原始資料；學員放入，AI 不改原文
├── 知識庫/          # AI 整理、更新與連結的知識
│   └── index.md
├── 創作庫/          # 報告、文案、簡報、腳本等成果
└── 工作日誌/
    └── log.md        # 只追加，不改寫歷史
```

資料逐漸增加時，才在四個資料夾底下新增同名專案子目錄。不要為了整齊預先建立大量空分類。

需要建立檔案時，讀取 [專案範本](references/project-templates.md)。需要向學員介紹安裝、口令或理念來源時，讀取 [學員使用指南](references/learner-guide.md)。

## 共通寫入規則

任何新增或修改檔案前，先顯示一次預覽：

```text
準備寫入：
- 位置：<目標相對路徑>
- 類型：原始資料／知識／成果／日誌
- 摘要：<1-3 句>
- 來源：<網址、附件名、對話或學員口述>

要保存嗎？
```

學員確認後才寫入。若學員要求調整位置或內容，更新預覽，不要先寫再搬。對同一批已確認的檔案不重複詢問。

寫入時遵守：

- `Clippings/` 原始檔不可被 AI 靜默改寫；需要清理格式時建立新副本並保留來源。
- `知識庫/` 每個主題一頁，更新既有主題優先於建立近義重複頁。
- `創作庫/` 保存可交付或可再利用的成品，不把每段聊天都當成果。
- `工作日誌/log.md` 只能追加；`handoff.md` 保持精簡，可於收工時重寫。
- 每張知識至少保留 `sources`、`created`、`updated`；有專案時加 `project`。
- 清楚區分來源事實、AI 綜合、待確認事項。新舊來源衝突時保留雙方與日期，不靜默覆蓋。

## 操作模式

### 初始化

當使用者要求建立或初始化第二大腦：

1. 掃描目前資料夾與既有 `AGENTS.md`、`handoff.md`，先說明會沿用與補哪些缺口。
2. 確認這是學員唯一的共用二腦；若已有另一個二腦，先讓學員選擇沿用或合併規劃，不另建競爭真相源。
3. 依專案範本提出建立清單，取得確認後建立最小架構。
4. 在 `AGENTS.md` 登記第二大腦狀態與四個相對路徑，供開工／收工偵測。
5. 不自動初始化 Git、安裝 Obsidian、建立排程或呼叫 API；需要時另行說明與取得授權。

### 收錄原始資料

當使用者說「把這份資料收進二腦」：

1. 取得專案名稱；已有上下文就直接推定，不重問。
2. 確認來源類型與可追溯資訊：網址、附件檔名、作者或提供者、取得日期。
3. 先執行下方的資料安全告知，再預覽 `Clippings/<專案>/...`。
4. 確認後保存原文或忠實轉存版本，不在原始層加入 AI 推論。
5. 詢問是否現在整理成知識；沒有要求就停在 Clippings。

### 整理成知識

1. 先讀 `知識庫/index.md` 並搜尋同主題頁，避免重複建立。
2. 從來源提取關鍵事實、觀點、時間、人物／組織、關係、行動項目與不確定性。
3. 提出準備新增或更新的頁面清單與摘要，取得確認後才寫入。
4. 更新相關頁面與必要的 `[[雙向連結]]`，再更新 `知識庫/index.md`。
5. 在 `工作日誌/log.md` 追加一筆整理紀錄，包含日期、操作、頁面與來源。
6. 最後檢查來源可追溯性、重複頁、斷鏈與內容衝突。

不要預設一份來源必須拆成很多頁；只建立未來確實會重用的知識。

### 查詢

1. 先讀 `知識庫/index.md`，再搜尋並讀取相關知識頁。
2. 只有需要核對、補充或解決衝突時才讀 `Clippings/` 原始資料。
3. 回答要標示所依據的知識頁與原始來源；找不到就明說「目前二腦沒有足夠資料」。
4. 若查詢產生有長期價值的新分析，先預覽並詢問是否存回 `知識庫/` 或 `創作庫/`。

### 保存成果

當使用者要求保存剛才成果：

1. 判斷它是可交付成品還是可重用知識。
2. 成品預覽到 `創作庫/<專案>/`；知識預覽到 `知識庫/<專案>/`。
3. 註明使用了哪些來源與知識頁。
4. 取得確認後寫入，必要時更新索引與日誌。

### 健檢

當使用者說「檢查二腦」時，只做唯讀檢查並回報：

- 沒有來源或來源路徑失效的知識頁。
- 重複或近義頁面。
- 新舊內容衝突與過期資訊。
- 未被索引的頁面、孤立頁與斷裂連結。
- 只有對話紀錄、尚未落地的成果。

先提出修正清單；未取得確認不得批次改寫。

## 資料安全告知

目標是盡告知義務與提供安全選項，不替學員作最終決定。

若資料可能含個人或公司內部資訊，在處理前提醒一次：

> 這份資料可能包含個人或公司內部資訊。建議先代號化，並確認您有權交由 AI 處理。您可以選擇「幫我代號化」；若了解風險且仍要使用原始資料，請明確告訴我繼續。

- 學員選擇代號化：先提出欄位與代號方案，確認後產生去識別副本；原檔不寫進 AI 二腦。
- 學員確認有權且接受風險：繼續處理，不反覆勸阻；在來源 metadata 記錄 `privacy_decision: user-confirmed-original-data`，不要把敏感內容抄進日誌。
- 學員已在同一請求中清楚確認時，不再重問。
- 同意在本機二腦使用原始資料，不等於同意提交到 Git、公開或同步到第三方；這些外部動作須各自取得授權。
- 要把資料送往另一個外部網站、Plugin、MCP 或 API 時，該次傳輸仍須另外告知與確認。

API key、token、密碼、Cookie、私鑰、驗證碼、助記詞等帳號安全憑證不得收錄或複製。發現後停止處理該值，提醒撤銷／輪替並改用環境變數名稱；學員同意也不解除此限制。

## 與開工／收工整合

本 Skill 不接管「開工」與「收工」觸發詞，避免與 `startup`、`shutdown` 衝突。初始化後由 `AGENTS.md` 的「第二大腦」區塊作為整合契約：

- `startup` 開工時唯讀 `handoff.md`、`知識庫/index.md` 和 `工作日誌/log.md` 最近紀錄，再按任務讀相關知識。
- `shutdown` 收工時盤點準備保存的 Clippings、知識與成果，先預覽確認，再寫入、更新索引並追加日誌。
- 沒有啟用標記或缺少二腦路徑時，兩個 Skill 維持原流程，不猜測、不自動建立。

## 邊界

- Obsidian 是建議安裝的 Markdown 閱讀與關係圖工具，不是資料庫本體，也不是使用本 Skill 的必要條件。
- 初學版不需要 embeddings、向量資料庫、MCP、Notion 同步或 `compile.py`。
- 不預設每日自動整理。先手動使用；穩定後可提議每週提醒，建立任何排程前另行確認頻率、費用與寫入範圍。
- 不自動上傳、寄送、公開、commit 或 push。Git 行為交給專案既有治理與 `shutdown`。
- 團隊型、多 repo、跨 Agent 生產環境應使用其既有治理，不以本學員版覆蓋。
